# Comparison media and session binding

This follow-up connects local media binding and playback-record import to the existing hosted V2 acceptance function and creator-parity scorer CLI. It preserves production approval/publication false in binding receipts and does not infer perception from decoding or player events.

## Review inputs and workflow

1. Load authorized candidate/reference files in the existing `/compare` workspace. It hashes the same browser Files used for playback. Each accepted file selection creates a new session ID. Export each reference pair's notes/session records, then collect the exported objects in a JSON array (`sessions.json`). Choose and play each audio track separately. Muted, skipped, stalled or otherwise unrecorded intervals do not count toward unmuted playback coverage.
2. Supply `references.json`: an array of 2..20 `{ "url": "https://...", "path": "local/reference.mp4" }` objects. Paths resolve relative to that manifest. URLs must exactly match submitted comparisons. Nothing is fetched from those URLs.
3. Independently perform the audiovisual review. In the existing reviewer report, set root `review_session_id` to the candidate session and each comparison's `review_session_id` to its reference session. Preserve separate actual audiovisual observations, full-review declarations and reviewed intervals. Copying playback intervals into observation fields without actual review is not valid evidence.
4. Run:

```
node scripts/exact_av_review.mjs validate-bound candidate.mp4 result.json review.json references.json sessions.json
```

The shared validator independently hashes, probes and fully decodes both streams for all supplied files. Bound inputs must be direct MP4 containers: the header is checked from bytes, the MOV/MP4 demuxer is forced, only the file protocol is allowed, and external data references/absolute alias paths are disabled. Renaming a playlist to `.mp4` does not permit it. URLs are labels, never fetch instructions. It compares actual hashes, sizes and durations with reports and session records; checks coverage against measured durations; rechecks media hashes and manifest/session-file hashes; and blocks missing, changed or mismatched inputs. Successful output includes imported sessions separately from reviewer observations and a runtime binding of the review digest, exact input hashes and file versions. The original `validate` command remains structural-only for existing preparation/diagnostic workflows and is not a substitute for this gate.

## Honest scope and operational limits

Player telemetry records media progression and unmuted routing, not frame-by-frame display, audible hardware output, attention or semantic perception. Hidden, paused, seeking, stalled, replacement and rate/volume boundaries break continuity. Missing boundary samples fail closed; replay unrecorded portions rather than filling gaps manually. Session IDs correlate files and reviewer records; they do not authenticate a reviewer. Exported JSON and observation prose remain editable claims. Hashing cannot authenticate the footage-to-source-URL association. All bound results explicitly retain `perception_verified:false` and `production_approved:false`; separate authentic review remains required.

Expensive probing/decoding runs only in explicit validation, with a shared five-minute subprocess deadline. Public health/watch/media requests never launch probes or decoders. On first use of a receipt, a single asynchronous, streaming hash admission verifies every input (30-second deadline, 512 MiB per input, 2 GiB total); requests remain blocked while it runs. Concurrent requests cannot launch more admissions. Once admitted, requests check bounded receipt JSON and filesystem identity/size/mtime/ctime for every input. Any modification, replacement, missing file, review digest change or receipt mismatch blocks immediately and requires explicit revalidation. Even restoring the original bytes after a modification requires a new receipt. Files must remain stable while served. These are local trusted validator receipts, not signed reviewer attestations or protection against an administrator forging all evidence. No background production jobs, infrastructure or credentials were added.

The synthetic HTTP regression exercises the actual production health/watch/media handlers over a loopback HTTP server, with unrelated services excluded. It sends 30 concurrent cold requests and 90 warm requests including 30 successful byte ranges. Cold requests share one asynchronous admission; warm requests do not rehash or decode. Same-size reference mutation with restored mtime blocks health and media. The first Windows run measured a 25.1 ms timer delay during cold concurrency. This establishes technical operation only.
